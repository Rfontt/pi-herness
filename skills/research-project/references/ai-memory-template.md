# .ai/ engineering memory — project template

Fill in every placeholder (`<...>`). Delete files/sections that don't apply. Keep one subject per
file, date each file, and tag every claim FACT / DECISION / LESSON / CONTEXT. Every file ends with a
`Sources` line listing the `file:line` (or build-config key) that backs its claims — so staleness is
detectable later.

**Layer-scoping rule (the point of this layout):** one file per layer / concern, so an agent working
on `application` loads `architecture/application.md`, NOT the whole service. `overview.md` is a thin
map with a routing table — never a dump. The README carries the same routing table so the agent knows
which files to load for a given task.

Full directory shape:

```
.ai/
├── README.md                  # index: routing table + workflow obligations
├── architecture/
│   ├── overview.md            # the map: identity, deployables, module tree, dependency direction, wiring
│   ├── domain.md              # entities, value objects, ports, exceptions, domain invariants + rules
│   ├── application.md         # commands/queries + handlers, use cases, orchestration, handler rules
│   ├── http.md                # inbound HTTP (routers, handlers, DTOs, error mapping) — if present
│   ├── messaging.md           # inbound events (consumers, converters, event→command bridges) — if present
│   ├── persistence.md         # DB (repositories, migrations) — if present
│   ├── downstream.md          # outbound clients + circuit breakers — if present
│   ├── runtime-config.md      # (optional) resilience, messaging, feature flags, timeouts
│   └── flows.md               # cross-layer end-to-end flows (each referencing the layer files it spans)
├── context/
│   ├── build.md               # build system, commands, workflow obligations
│   ├── libs.md                # platform + runtime + test libraries (mechanism, not exhaustive dump)
│   ├── code-style.md          # naming, comments, logging, error handling, metrics
│   ├── test-style.md          # framework, file organization, mocking, per-layer patterns
│   ├── lint.md                # (optional) linter/formatter config + rules in effect
│   └── code-review.md         # (optional) → generated by the code-review-ruleset skill, NOT here
├── decisions/                 # ADR-style (populated over time — not part of bootstrap)
├── incidents/                 # postmortems (populated over time — not part of bootstrap)
└── lessons/                   # hard-won lessons (populated over time — not part of bootstrap)
```

The adapter files are generated per adapter KIND actually present. Common kinds and file names:
`http.md` (inbound HTTP), `messaging.md` (inbound events), `persistence.md` (DB), `downstream.md`
(outbound service clients). Rename to match the stack (e.g. `grpc.md`, `cache.md`, `s3.md`); skip kinds
the project doesn't have. One file per KIND, never one file per Gradle/Maven module.

```
# Engineering memory index

Last researched: <YYYY-MM-DD>

## Routing — load only the slice the task touches
| Task touches…                                   | Load |
|-------------------------------------------------|------|
| orientation / anything                          | architecture/overview.md |

| application (handler, use case, orchestration)  | architecture/application.md |

| events / consumer                               | architecture/messaging.md |
| DB / migration                                  | architecture/persistence.md |
| external service call                           | architecture/downstream.md |
| full flow across layers                         | architecture/flows.md |
| resilience / feature flags / timeouts           | architecture/runtime-config.md |

Always (cross-cutting): context/code-style.md, context/test-style.md, context/build.md.

## Files (load as needed)
- architecture/overview.md — identity + module layout + dependency direction + wiring.
- architecture/domain.md — entities, VOs, ports, exceptions, invariants.
- architecture/application.md — handlers, use cases, orchestration.
- architecture/<adapter-kind>.md — adapters by kind (http / messaging / persistence / downstream).
- architecture/flows.md — end-to-end flows + deviations.
- context/build.md — build/test/lint/format commands + workflow obligations.
- context/libs.md — libraries + versions.
- context/code-style.md — code conventions.
- context/test-style.md — test conventions.

## Workflow obligations (ALWAYS before finalizing a change)
- [ ] <format command>   (mandatory)
- [ ] <lint command>
- [ ] <test command for the affected module(s)>
```

The README is the entry point the harness reads first, so the routing table here is what makes the
step (and format/lint) fire on every plan/spec.
